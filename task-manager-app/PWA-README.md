# Solution B — Installable Angular PWA (localhost only, no public hosting)

Implements CLAUDE.md §13–§15. Same app as Solution A (`index.html` at the repo
root): same data model, same recurrence engine, same `ptm_data` backup format,
same dark UI. Different shell — an Angular application that can be installed to
a phone's home screen and launched full-screen, without a domain, a public
host, or a backend.

## Files

```
/pwa                        Angular workspace (Angular 22, standalone, zoneless)
  angular.json              build config; critical-CSS inlining is off on purpose (see CSP)
  ngsw-config.json          §13.4 — which files the service worker prefetches
  public/                   copied verbatim into the build output
    manifest.webmanifest    §13.3
    icon-192.png            §13.5 — generated, not hand-drawn
    icon-512.png
  src/
    index.html              CSP, viewport, manifest link, iOS meta tags
    styles.css              the whole §8 stylesheet, global (shared vocabulary with Solution A)
    app/
      app.ts/.html          shell: topbar + routed page + bottom tabs + toast
      app.routes.ts         §7's three pages, lazily loaded
      app.config.ts         router (hash location) + service worker registration
      core/                 all the logic, framework-free where it can be
        date.ts             §4 calendar arithmetic, "YYYY-MM-DD" strings only
        recurrence.ts       §4.1 lastDueDate / nextDueDate / labels
        model.ts            §3 types + limits
        validation.ts       §9 strict import validation
        task-store.ts       §6 sections, completion, cycle reset, import/merge
        icons.ts            §5 icon set, as shape data rather than markup
        chrome.ts           what each page contributes to the topbar
        toast.ts            transient confirmations
        shell-status.ts     §14 "Offline install" reporting
      pages/                home, home-list, tasks, task-editor, settings
      ui/icon.ts            renders an icon without innerHTML or the sanitizer
  dist/tasks/browser/       build output — this is what gets served (gitignored)
/tools
  make-icons.js             one-time icon build step (§13.5), zero dependencies
  make-cert.js              one-time local CA + certificate for --https (§14 path 5)
  serve.js                  static server for the build output (§13.6), zero dependencies
  certs/                    generated by make-cert.js — gitignored, holds a private CA key
```

The scripts under `/tools` are build/dev helpers — never shipped, never fetched,
and the app never runs them. `make-cert.js` shells out to `openssl`; everything
else is dependency-free Node.

## Build and run

```
cd pwa
npm install
npm run build          # -> pwa/dist/tasks/browser
cd ..
node tools/serve.js    # http://localhost:8000, loopback only
```

`tools/serve.js` serves the **build output**, not the source. That matters: the
service worker only exists in a production build, so this is the only mode in
which offline install can be tested.

For editing, `cd pwa && npm start` gives a live-reload dev server at
`http://localhost:4200` — but with the service worker deliberately disabled.
The Settings page says so rather than claiming a false "offline ready".

Other server flags:

```
node tools/serve.js 8080       # custom port
node tools/serve.js --https    # https://<lan-ip>:8443 with a local certificate — the phone route
node tools/serve.js --adb      # also forward the port to a USB-connected Android phone
node tools/serve.js --lan      # also reachable from the LAN (iOS; NOT offline-capable, see below)
```

Then open `http://localhost:8000` — Chrome/Edge will offer **Install app**.

The server is only needed for the *first* load on each device. Once the service
worker has cached the shell, the installed app opens with the server stopped
and the PC off.

```
cd pwa && npm test         # watch mode
cd pwa && npm run test:run # single run
```

64 tests: the recurrence engine against every §12 edge case, the strict import
validation, the store's section/completion rules, and a rendering pass over all
five pages.

## The LAN-IP trap (read this if offline isn't working)

**Symptom:** the app only runs while `node tools/serve.js --lan` is up, and the
"installed" icon opens a Chrome tab showing `http://192.168.x.x:8000` instead of
a full-screen app.

**Cause:** service workers require a *secure context* — `https`, `localhost`, or
`127.0.0.1`. A LAN IP is none of those, so on that origin
`navigator.serviceWorker` is simply **undefined**. Nothing registers, nothing is
ever cached, and §13.4's offline guarantee never takes effect. Chrome then also
fails its install criteria, so **Install app** quietly degrades to a plain *Add
to Home screen* **shortcut** — a bookmark that opens in a browser tab and dies
with the server. That is not a PWA.

The app tells you this directly: **Settings → "Offline install"**. It reads
*"Offline ready — N shell file(s) cached"* when the service worker is doing its
job, and shows a red banner naming the offending origin when it isn't. Check it
before unplugging.

**Fix — get the phone onto a secure origin.** Three ways:

- **A) Real HTTPS on the LAN IP (recommended).** `tools/make-cert.js` issues a
  local certificate; the phone trusts it once. No USB, no flag, and it is the
  only route that also removes the address bar. Step-by-step below.
- **B) Chrome flag.** Cheapest, and it does fix offline — but the installed app
  keeps a browser address bar, because the flag relaxes the secure-context check
  that gates service workers, not the install itself. See below.
- **C) `adb reverse`.** Real `localhost` on the phone, so also chromeless — but
  it needs Android SDK Platform Tools and USB debugging. See §14 further down.

### The address bar (read this if the icon opens in a Chrome tab)

`display: "standalone"` in the manifest is necessary but not sufficient. Chrome
keeps browser UI over an installed app whose origin is not genuinely secure:
over plain `http` it commonly turns **Install app** into a bookmark shortcut that
opens in an ordinary tab. Route **B** does not change that — only a real secure
origin does, which means route **A** (https) or route **C** (`localhost`).

So: an address bar on the installed app is a symptom of the **origin**, not of
the manifest. Fix the origin; don't touch `display` / `display_override`.

### A) HTTPS on the LAN IP — the full fix

On the **PC**, once:

```
node tools/make-cert.js         # writes tools/certs/ (gitignored)
```

It creates a private CA (`rootCA.crt`, valid 10 years) and a leaf certificate
naming `localhost`, `127.0.0.1` and every LAN IPv4 this PC has. Nothing is
fetched; the keys never leave the machine.

It drives the `openssl` binary, which on Windows is usually **not** on PATH — so
the script finds the one Git for Windows ships (`C:\Program Files\Git\mingw64\bin\
openssl.exe`) and prints which one it used. Works the same from PowerShell or Git
Bash. Override with the `OPENSSL` environment variable if you have another copy
you'd rather use.

Then, every time you want to serve:

```
cd pwa && npm run build && cd ..
node tools/serve.js --https     # https://<lan-ip>:8443
```

It also opens a small plain-`http` page on port 8000 that does nothing but hand
out the CA and repeat these steps — the phone can't fetch the CA over the very
connection the CA exists to validate, so that page is deliberately unencrypted
and serves no app files.

On the **phone**:

1. Open `http://<pc-ip>:8000` (the address the server prints) and tap
   **Download rootCA.crt**.
2. **Settings → Security → More security settings → Encryption & credentials →
   Install a certificate → CA certificate → Install anyway**, then pick the
   downloaded `rootCA.crt`. Wording varies by phone; searching Settings for
   *certificate* finds it. Android will warn that a third party may monitor
   traffic — that third party is this PC's CA, which only signs this one
   certificate.
3. Fully close Chrome and reopen it.
4. Go to `https://<pc-ip>:8443`. No certificate warning, and the padlock is real.
5. **Settings → Offline install** must read *"Offline ready — N shell file(s)
   cached"*.
6. Chrome ⋮ → **Install app**. The launched app has no address bar.
7. Stop the server and reopen from the home screen to prove it's offline.

**Caveats:**

- `tools/certs/` holds a **private CA key**. It is gitignored and must stay on
  this PC. If it ever leaks, delete `tools/certs/`, re-run `make-cert.js`, and
  remove the old CA from the phone under *Settings → Encryption & credentials →
  Trusted credentials → User*.
- The leaf is valid 397 days; re-run `make-cert.js` after that. A DHCP change
  also needs a re-run — but it **reuses the existing CA**, so the phone never has
  to trust anything twice.
- `https://<ip>:8443` is a different origin from `http://<ip>:8000` →
  **different `localStorage`**. Export first, restore after. See the warning
  below.

### B) Chrome flag — offline only, address bar stays

On the **PC**:

```
cd pwa && npm run build && cd ..
node tools/serve.js --lan
```

It prints the LAN origin to use. On the **phone**, in Chrome:

1. Go to:
   ```
   chrome://flags/#unsafely-treat-insecure-origin-as-secure
   ```
2. In the text box, enter the origin the server printed — for this machine it was:
   ```
   http://192.168.100.28:8000
   ```
   Origin only: scheme, IP and port, **no trailing slash and no path**. Multiple
   origins can be comma-separated.
3. Set the dropdown next to it to **Enabled**.
4. Tap **Relaunch** at the bottom. The flag does not take effect until Chrome restarts.
5. Browse to `http://192.168.100.28:8000`. Chrome now treats it as a secure origin,
   so the service worker registers and caches the shell.
6. Check **Settings → Offline install** — it must read *"Offline ready — 11 shell
   file(s) cached"*. If it still shows the red banner, the flag didn't apply (most
   often: a typo, a trailing slash, or Chrome wasn't relaunched).
7. Chrome's ⋮ menu may now offer **Install app**. Install it — but see the caveat
   below: on an `http` origin the result is usually still a shortcut that opens in
   a Chrome tab, address bar included.
8. Stop the server on the PC and reopen the app from the home screen to prove it's
   genuinely offline.

**Caveats for this route:**

- **The address bar stays.** This flag buys the service worker (so offline works),
  not a chromeless install. Chrome treats an `http` origin as insecure for install
  purposes regardless of the flag, so the home-screen icon opens in a browser tab.
  Use route **A** if that matters. The app says so too, under
  *Settings → Offline install*, when it detects it is cached on an `http` origin.

- The flag is tied to that **exact origin string**. If your router hands the PC a
  different IP, the flag no longer matches — reserve/static-assign the PC's IP in
  the router if you plan to reinstall or re-cache later. An *already installed* copy
  keeps working from its cache regardless, since it never needs the network again.
- The port matters too: `http://192.168.100.28:8000` ≠ `...:8080`. Keep using the
  same port (the `serve.js` default is 8000).
- This flag lowers a real browser security guarantee for that one origin. It only
  affects this phone's Chrome and only that address — but don't leave a public or
  untrusted origin in there, and clear it if you stop using this setup.

### ⚠️ Your existing tasks follow the origin, not the app

`localStorage` is scoped **per origin** — scheme + host + port. The Angular
rewrite does not change this either way:

- **Same origin as before (e.g. still `http://192.168.100.28:8000`): your tasks
  are still there.** The rewrite changed what the server sends, not where it
  sends it from. Nothing to migrate.
- **Route A (https): data does NOT follow.** `https://192.168.100.28:8443` is a
  different scheme *and* port from `http://192.168.100.28:8000`, so it is a
  different origin with its own empty `localStorage`. Export first — this is the
  one step people skip.
- **Route B (Chrome flag): data is preserved.** The flag only changes how Chrome
  *classifies* that origin, not the origin itself.
- **Route C (`adb reverse`): data does NOT follow.** You move from
  `http://192.168.100.28:8000` to `http://localhost:8000` — a different origin, so
  a different `localStorage`, and the app will look empty.

Migrating for routes A and C (or any origin change, including the PC's IP changing):

1. Open the current app → **Settings → Export JSON**.
2. Delete the old home-screen icon.
3. Install from the new origin.
4. In the newly installed app → **Settings → Restore** → pick that file → **Replace all**.

Skipping this looks exactly like "the app lost all my tasks." Export before any
origin change regardless — it costs one tap.

## Installing on a phone (§14)

`localhost` is per-device, so the phone browsing to your PC's LAN IP is **not** an
installable origin in Chromium — unless you tell Chrome to trust it. Options, best
first for this setup:

0. **Android + real HTTPS over LAN — ✅ the route used here.** No USB, no cable,
   nothing on the PC beyond Node and `openssl`. Full recipe in *"A) HTTPS on the LAN
   IP"* above; the short version is `node tools/make-cert.js`, then
   `node tools/serve.js --https`, then trust `rootCA.crt` on the phone once and open
   `https://<pc-ip>:8443`. It is the only LAN route with no address bar. §14 lists
   this as path 5; it satisfies the same constraint as the rest — no domain, no
   public host, no backend, nothing reachable from outside the LAN.

   The earlier route — `chrome://flags/#unsafely-treat-insecure-origin-as-secure`
   pointed at `http://192.168.100.28:8000` — still works for *offline*, and is kept
   above as route B, but it leaves the installed app in a browser tab.
1. **Android + Chrome over USB (most reliable long-term).** Requires `adb` from the
   *Android SDK Platform Tools* — a standalone zip, no Android Studio needed;
   unzip it and put the folder on your `PATH`. On the phone enable *Developer
   options → USB debugging*, plug it in, accept the "Allow USB debugging?" prompt,
   then:
   ```
   node tools/serve.js --adb
   ```
   which starts the server and runs `adb reverse tcp:8000 tcp:8000` for you (it
   reports clearly if adb is missing or the phone isn't authorised). Now open
   `http://localhost:8000` in Chrome **on the phone** — genuinely localhost from the
   phone's point of view, so the install prompt is a real one.

   Confirm **Settings → Offline install** says *Offline ready* **before** unplugging.
2. **Fully on-device.** Install Termux, run a static server there against a copy of
   `pwa/dist/tasks/browser`, open `http://localhost:PORT` in Chrome on that phone.
3. **iOS Safari.** Run `node tools/serve.js --lan`, open `http://<pc-ip>:8000` in
   Safari, then Share → *Add to Home Screen*. Safari is historically more lenient
   than Chromium about the install gesture — but the service-worker rule still
   applies, so verify the Offline install card there too. `adb reverse` is
   Android-only and does not apply.

## Shipping an update

```
cd pwa && npm run build
```

That is the whole procedure. The Angular service worker versions itself from a
content hash of the built files (`ngsw.json`), so there is **no cache constant to
bump by hand** any more — the manual `CACHE = 'ptm-shell-vN'` step the old
handwritten `sw.js` needed is gone, along with the class of bug where forgetting
it left installed copies serving a stale shell forever.

An installed copy picks the update up on its next launch. If the app is open when
a new version finishes downloading, Settings shows *"A newer version has been
downloaded"* with a **Reload to update** button.

Icons only need regenerating if the glyph or palette changes:
`node tools/make-icons.js` (writes into `pwa/public/`).

## Deviations from the spec

1. **Angular, so Solution B has a build step and npm dependencies.** §2's
   "zero dependencies, no build step" is a Solution A constraint and still holds
   there — the root `index.html` is untouched, still one file, still opens from
   `file://`. Solution B trades that for a real framework. The runtime output is
   still self-contained: no CDN, no web font, no third-party origin, no network
   call of any kind.
2. **§15's "reuse Solution A's HTML/CSS/JS as-is" no longer holds literally.**
   The CSS is byte-for-byte the same stylesheet; the logic is a direct port to
   TypeScript, function by function. See *Keeping the two targets in sync* below
   for why this is the honest tradeoff and how the risk is contained.
3. **CSP differs from §9's literal text, and is stricter.** §9 assumes inline
   `<script>`; Angular ships real script files, so `script-src` is `'self'` with
   no `'unsafe-inline'` at all. Added: `manifest-src 'self'` (read the manifest),
   `worker-src 'self'` (register the worker), `connect-src 'self'` (the worker
   fetching shell files). All same-origin, so §15's "never reference a
   third-party origin" holds. `frame-ancestors` is omitted deliberately —
   browsers ignore it in a `<meta>` CSP and log an error for it.
4. **Critical-CSS inlining is disabled** in `angular.json`. Angular's inliner
   emits `<link ... onload="this.media='all'">`, an inline event handler that the
   CSP above rightly blocks — which would leave the app with only the inlined
   critical CSS and no full stylesheet. Turning it off costs one extra local
   stylesheet request and removes the inline handler entirely.
5. **Hash-based routing** (`#/tasks`). Path routing would require every static
   server that ever hosts this folder to rewrite unknown paths to `index.html`;
   §13.6's promise is "any static file server". Hash routing needs no such rule.
6. **Node server instead of `python3 -m http.server`.** Python is absent on this
   machine. §13.6 allows any static server; `tools/serve.js` is loopback-only by
   default and serves nothing outside the build output.
7. **An "Offline install" card on the Settings page.** Not in §7.3. Added
   because a failed service-worker registration is silent, which is what made the
   LAN-IP trap so hard to diagnose. It reports status only — reads no task data,
   writes nothing.

Additions beyond the minimum manifest: `maskable` icon purposes (the glyph sits
inside the maskable safe zone, so Android won't crop it), `theme_color`/
`background_color` from §8's palette, and the `apple-mobile-web-app-*` meta tags
Safari needs for path 3 above.

## Keeping the two targets in sync (§15)

§15 says never fork the task/recurrence logic between the two targets. Solution
A is a single dependency-free `.html` file and Solution B is now TypeScript
compiled by Angular, so there is no longer a literal shared source file — the
logic exists twice.

What contains that risk:

- **The port is function-for-function.** `date.ts` and `recurrence.ts` are the
  same algorithms with the same names as Solution A's `lastDueDate`,
  `nextDueDate`, `weekDaysList`, `nthWeekday`, `occurrenceInMonth`.
- **The engine has tests now, which Solution A never did.** `recurrence.spec.ts`
  pins every rule in §4.1 and every edge case in §12. A behaviour change in
  either target shows up as a failing expectation rather than as a task
  quietly appearing on the wrong day.
- **The data format is the contract.** Both targets read and write the same
  `ptm_data` shape, and `validation.ts` enforces it on import. A backup exported
  from one imports into the other — that is the property worth protecting, and
  it is checked by `validation.spec.ts` against the documented schema.

If the two ever disagree, the tests here are the tiebreaker: they encode what
CLAUDE.md §4 actually specifies.

## What was verified

Built with `ng build` (production), served by `tools/serve.js`, driven with real
headless Chrome over the DevTools protocol:

- **App boots and renders** — shell, topbar, bottom tabs, page content, icons as
  real SVG elements.
- **Service worker registers and reaches `activated`**, scope `/`.
- **11 shell files cached** across `ngsw:…:assets:app:cache` (9) and
  `…:assets:icons:cache` (2) — every JS chunk, the stylesheet, `index.html`,
  the manifest and both icons.
- **The app loads and renders with the server stopped** — the whole point of
  §13.4. Verified by killing the server process and reloading.
- **Settings reports "Offline ready — 11 shell file(s) cached."**
- **No console errors and no CSP violations** on load.
- **Only same-origin requests** are made.
- `tools/serve.js` refuses to start without a build, and serves
  `manifest.webmanifest` as `application/manifest+json`.
- 64 unit/rendering tests pass.

**The HTTPS route (§14 path 5), verified on this machine:**

- `node tools/make-cert.js` produces a chain that validates: leaf `CA:FALSE`,
  `extendedKeyUsage=serverAuth`, SAN `DNS:localhost, IP:127.0.0.1,
  IP:192.168.100.28`, signed by the CA (`openssl verify` → OK, and
  `openssl s_client` against the running server → *Verify return code: 0 (ok)*).
- `node tools/serve.js --https` serves the build over TLS on 8443 with the same
  headers as the http path (`Service-Worker-Allowed: /`,
  `application/manifest+json`, traversal outside the build root refused), and the
  plain-http helper on 8000 hands out `rootCA.crt` as
  `application/x-x509-ca-cert`.
- Real Chrome pointed at **`https://192.168.100.28:8443`** — a LAN IP, no
  `chrome://flags` override, the certificate trusted only via its SPKI pin so
  verification stayed on — reports `isSecureContext: true`, registers the service
  worker to `activated`, and caches the full shell (14 cache entries). That is the
  exact condition route B could never reach.

**Not verified here:** the install itself on the phone. Everything Chrome checks
before offering **Install app** is confirmed above (secure origin, manifest,
icons, active service worker), but whether Android mints a full WebAPK for a
LAN-IP origin — as opposed to a standalone-mode install — can only be seen on the
device. Either way it is a genuinely secure origin now, which is the part that was
missing. Also unverified: the `--adb` flag (no `adb` on this machine) and the iOS
Safari path.

**On real hardware (Android + Chrome):** route B — the
`unsafely-treat-insecure-origin-as-secure` flag set to `http://192.168.100.28:8000`
— was confirmed caching offline end to end **for the previous, handwritten build**.
Its home-screen icon still opens with an address bar, which is what route A fixes.
